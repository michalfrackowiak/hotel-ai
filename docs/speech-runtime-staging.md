# Speech controller and admin staging

The **Stage the private controller and Django speech-switch flow** check in GitHub Actions exercises the 0.5 runtime on a disposable Linux runner. It uses the pinned Piper and Vosk images already built by the bilingual CI check, the controller's actual Linux startup command, and Django's request stack with CSRF checks enabled. The fixture runs a private controller on loopback and starts Django in the same network namespace so the admin client can reach that listener.

The runner stops the previous CI services before staging. The drill creates its own private bridge, four approved speech containers, and a temporary directory containing a fictional booking database, route store, controller journal and manifest. It starts one Piper and one Vosk worker, with room to overlap one replacement at a time. Each worker has a half-CPU limit. The maximum speech allocation is 4 GiB, and the initial capacity check also accounts for Django's 512 MiB limit and 1 GiB of headroom. Django runs as an unprivileged user with only the fixture data directory mounted. Worker ports stay on the bridge. Credentials and request data are created for the run and discarded with the fixture.

The drill covers a controller startup check, recovery of a deliberately seeded unfinished request, confirmation of all four planned switches, and speech requests routed through Django. It checks that the English switch preserves the shared worker for the Polish slot and that the old worker stops after its last slot moves. The test client starts with a fixture staff session and exercises the actual permissions and CSRF checks. Both languages request Piper audio and send one second of synthetic silence to Vosk. Their booking drafts persist across the switch sequence.

The recovery case uses a seeded journal interruption to make the test repeatable. It exercises the actual runtime's recovery, model readiness and admission checks. The existing isolated Docker lifecycle check covers simulated publication failure and readiness rollback separately. This stage uses two instances of each pinned model image to verify switching between deployments with identical inference contracts.

The scripts accept execution on hosted GitHub Actions runners. Run the repository's `Checks` workflow through a pull request to repeat the drill. The Linux x86-64 run covers the private runtime and admin flow. Production activation still depends on server-specific ARM64 capacity, endpoint approvals, network wiring, and backup and recovery checks. Synthetic silence and text exercise requests through both speech services. Physical microphone evaluation and long-running workloads are tracked separately.

The hosted drill then stops the controller and returns its original workers to service for a fixed-endpoint fallback. A separate Django fixture uses a verified booking database restore, the same fixture signing key and the two original fixed endpoints. It checks speech from the restored drafts and retention of switch and recovery audit history. [Rollout and rollback procedure](speech-production-rollout.md)

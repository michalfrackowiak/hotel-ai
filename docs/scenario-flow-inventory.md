# Booking scenario flow inventory

This inventory covers English (EN) and Polish (PL) text chat, browser voice, and inbound phone. The common flow lives in [conversation.py](../reception/conversation.py). A persisted stage controls what input is accepted. An editable prompt key controls how a stage or outcome is presented. One stage can have several prompts, and a single reply can combine two prompts.

## Current booking states and outcomes

| Persisted stage or outcome | Current input and transition | Prompt keys |
| --- | --- | --- |
| Web entry | The selected page language starts a new conversation. EN starts at `check_in` with its own greeting. PL starts at `welcome`. A same-language start resumes the draft except for supported legacy arrival prompts and older English welcome drafts. Reset or a different-language start replaces the draft. | EN `web_check_in`, PL `welcome` plus bilingual menu parts |
| `welcome` (web) / `language` (phone) | On the PL web path, an English selection goes to EN `check_in`. Otherwise the web menu enters PL `check_in`, processing a parsed date or range in the same turn. Phone accepts keypad 2 or spoken English, otherwise enters PL arrival and can process an arrival given during the menu. The old EN-first phone menu still accepts 1 for EN and 2 for PL via keypad only. Its Polish option line is hard-coded. | PL `welcome`, EN `welcome_english_option`, PL `welcome_polish_option` |
| `check_in` | An EN selection from PL switches language. A valid arrival leads to `check_out`. A valid arrival and departure pair leads straight to `guests`. A parsed but invalid date or date pair repeats arrival. An unparsed response or final silence at arrival enters `handover`. | `check_in`, EN `web_check_in` at direct entry, `stay_dates` + `guests` for a pair, `handover` |
| `check_out` | An absolute date or stay duration must produce a departure after arrival. Success enters `guests`; invalid input repeats departure with guidance. | `check_out`, `check_out_retry`, `guests` |
| `guests` | A positive whole number up to 32767 triggers the availability calculation. Available rooms lead to `room`; invalid input stays at `guests`. No rooms or a booking-domain error returns to a fresh `check_in` draft. | `guests`, `guests_retry`, `rooms`, `unavailable`, `offer_changed` |
| `room` | A valid room code or option number selects the quoted room and enters `confirm`. Invalid input keeps the offer. Browser voice and phone receive up to two offers when the guest count is submitted by voice; text chat can receive more. The phone also accepts an option digit. | `rooms` contains rendered `option` items with channel-specific wording |
| `confirm` | Affirmative consent enters `delivery` and retains or creates the booking idempotency key. A decline enters `cancelled`. Other input repeats the quote. | `confirm`, `delivery`, `cancelled` |
| `delivery` | Email or SMS selection opens the corresponding `email` or `phone` stage. Other input repeats the choice. | `delivery`, `email`, `phone` |
| `email` / `phone` | Valid contact input enters `contact_confirm`. Invalid input keeps the entry stage with a contextual retry. The guest can request reception, choose a different method, or return to the delivery choice. | `email`, `phone`, `invalid_email`, `invalid_phone`, `confirm_email`, `confirm_phone` |
| `contact_confirm` | Read back the current candidate. An affirmative answer submits the booking. A negative or change answer clears the candidate and returns to contact entry. A valid replacement gets its own readback. An unrecognized response retains the candidate. Delivery changes and handover clear it. A booking-domain contact error returns to entry; other booking errors start a fresh arrival draft for a new quote. | `confirm_email`, `confirm_phone`, `invalid_email`, `invalid_phone`, `offer_changed`, contact/delivery/handover prompts |
| `delivery_pending` | The booking exists and has a reference. When the selected method is configured or explicitly set to wait, poll while the dispatch is pending or sending, with a 25-second deadline evaluated at the next poll. Otherwise finish immediately with the pending-dispatch wording. Web polls; phone announces the wait and then redirects every two seconds. | `receipt_waiting` |
| `completed` | Terminal booking state. Confirm dispatch only on provider acceptance. A pending dispatch gets queued wording; a failed, missing, or still-sending result once waiting ends gets unverified wording. All endings include the booking reference. | `receipt_sent_email`, `receipt_sent_sms`, `receipt_pending`, `receipt_unconfirmed` + `receipt_reference` |
| `cancelled` | Terminal for the Neptun flow. Start a new draft to book again. | `cancelled` |
| `handover` | Terminal for automated booking turns. Web creates a staff-inbox thread and forwards the triggering text if present. Guests can exchange messages while it is open. The phone dials the configured reception number or announces unavailability and hangs up. | `handover`, phone `phone_handover_unavailable` |
| `ended` (phone) | Reached on an expired draft, the third missed turn outside language/arrival/receipt handling, or a completed transfer callback. An unsuccessful transfer announces unavailability. An accepted connection ends silently. | `phone_ended`, `phone_handover_unavailable`, or silence |

## Channel handling

- **Web text.** [views.py](../reception/views.py) and [chat.js](../reception/static/reception/chat.js) supply suggestions for arrival, stay length, guest count, and room option, with separate controls for contact readback. Polling serves receipt progress and staff messages. Reset closes an existing handover. Starting voice replays the bilingual welcome when a prior text welcome turn moved a PL draft to arrival without collecting a date. Starting voice also allows a return from a new handover without any messages, while an active staff conversation remains available in chat.
- **Browser voice.** [voice.js](../reception/static/reception/voice.js) renders the spoken prompt segment in chat during playback and submits the guest transcript through the shared message endpoint. The EN arrival begins with a silent two-second pause and then two five-second listening windows. PL uses two five-second listening windows. Bilingual welcome and arrival timeouts reach the server, while later voice-stage silence stops browser voice and leaves the draft available to continue by text. Speech startup, microphone, recognition, busy, playback, and network failures use browser status and fallback handling. Server TTS and STT can return 429 for busy, 503 for unavailable, or 409 for a stale speech render or turn.
- **Inbound phone.** [calls.py](../telephony/calls.py) owns persisted call state and [views.py](../telephony/views.py) translates it into Twilio `Say`, `Gather`, `Pause`, `Dial`, or `Hangup`. The menu has a two-second response window, default arrival gathering is ten seconds, and other ordinary turns default to seven seconds. Timed arrival segments replace the default gather with their own windows. Earlier empty windows continue to the next segment; the last empty window submits the timeout. Outside menu, arrival, and receipt waiting, the first two missed turns repeat with `phone_silence`. The third ends the call. Inactive drafts expire after 20 minutes; terminal calls are retained for one day. Reception dialing has a 20-second limit and a separate completion callback. Phone uses its own recognition and speech services through Twilio.
- **Revision and retry boundaries.** Web validates the request shape and rechecks language and revision before mutation. Stale or unsupported timeout requests return the current state with 409. Phone verifies signed callbacks, valid call identities, and revision; a replay of a stale turn returns the current reply. Neither path treats transport retry as a booking answer. [parser_review.py](../reception/parser_review.py) optionally applies reviewed parser corrections for supported stages and distinguishes chat input from transcribed voice.

## Older drafts

[Legacy progression](../reception/legacy_conversation.py) remains active for saved drafts without `flow: neptun`. Old `check_in` drafts enter the Neptun flow; other active legacy steps keep their sequencing and wording. [The compatibility adapter](../reception/conversation.py) applies the current contact readback and handles these cases.

| Older draft type | Persisted steps and recovery |
| --- | --- |
| Legacy basic booking | `check_out` → `guests` → `name` → `email` → `contact_confirm` → `confirm` → `completed`. The first available room is used and a printable guest name up to 150 characters is collected. Declining the quote returns to legacy arrival. An already-saved email in an old quote still receives readback after quote approval, with a return to email entry if the saved address is invalid. |
| Legacy browser scenario (`scenario: true`) | `check_out` → `guests` → `select` → `confirm` → `name` → `email` → `contact_confirm` → `completed`. It offers up to two room options and gets quote approval before collecting contact details. Declining enters terminal `cancelled`. |
| Persisted replies without prompt metadata | The current renderer can recognize built-in menu and arrival replies. Other unmapped replies retain their literal text. Legacy active states with literal replies have no corresponding live editor prompt unless the compatibility adapter attaches one. |

## Configuration boundary

[scenario.py](../reception/scenario.py), [scenario_editor.py](../reception/scenario_editor.py), and `ScenarioPrompt` currently provide shared language/key overrides for written text and voice segments. Blank text or segments use the corresponding built-in behavior. The editor validates required simple placeholders, segment limits, and pauses. Listen-during-pause applies to arrival prompts only, with a required final listening window. Browser and phone share voice overrides where they use the same key. Prompts are read from current admin settings at render time.

A versioned scenario needs explicit representations for persisted steps, presentation variants, and channel events such as silence, delivery poll, and transfer outcome. Keep browser speech errors, signed callback validation, and state revision checks at the channel boundary. Preserve required quote consent, current-contact confirmation, atomic booking creation and confirmation queueing, availability, price validation, and booking idempotency in the server actions. The exact behavior of resumed older drafts needs to remain available when new sessions begin using versioned scenarios.

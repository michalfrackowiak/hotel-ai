# Versioned booking scenario records

The reception app stores one scenario per Polish or English chat or voice scope. Each language can also have a shared template. A channel draft records the exact sealed shared version it inherits from in `base_version`. Leaving the field empty makes the draft independent. Shared templates have no parent.

A scenario can retain several versions, each with numbered identity, ordered steps and one destination per event from each source step. The graph belongs to one version. A saved step stays in its original version. Replace a transition to change its endpoints. Publication copies pinned shared defaults into the channel graph before sealing. The channel version keeps its base reference and its own effective graph. It inherits missing steps and transitions and any supported prompt field absent from the local step. Local prompt fields and positions take precedence, and only the selected channel’s wording is copied. Step configuration stores a structured JSON object behind the scenario step form. The draft graph validator checks a conservative subset of the existing booking transitions.

`published_at` identifies previously sealed versions. The scenario's `published_version` points to the current selection. Rollback selects a prior sealed version while retaining both versions and their graph records. The publish and rollback services require an active staff account with `reception.publish_scenario` and compare the current selection with the caller’s expected version. A staff review screen will also need the latest audit ID to detect changes that returned to the same selection. Publication validates the effective graph and writes the seal, selected pointer and audit record in the same SQLite write transaction. Shared templates use structural validation. Standalone and materialized chat and voice graphs must also pass outcome coverage. SQLite triggers guard sealed records against inserts and updates, and Django delete signals protect graph records and publication history on ordinary ORM deletion. Direct SQL deletion remains available for Django flush and operator recovery. Later migrations that rebuild these tables must recreate their triggers.

The service is internal. The existing scenario editor and guest flows continue to use the existing prompts. Staff publication controls and guest version pinning remain separate tasks.

## Draft editing and validation

Versioned scenario administration keeps proposed edits separate from live prompt edits. In Django admin, create a **Scenario** for the language and channel, then create a numbered **Scenario version**. Add **Scenario steps** and **Scenario transitions** with the same version. Reopen the version to see **Saved graph validation** and **Outcome coverage**. Django applies its usual model permissions to each entry. The validation preview requires permission to inspect both steps and transitions. To replace a transition, delete the draft transition and add its replacement. To remove a draft step, remove its connected transitions first. The version history and a pinned shared base identify exactly which records a draft refers to.

The draft validator checks graph structure and the approval path. It checks that the entry and required booking states exist, that steps are reachable, that events lead to permitted destinations, and that a completed booking can only follow both quote approval and contact approval. It permits explicitly designated same-step retries. Draft steps can use the supported wording and voice segment settings. The admin preview validates standalone graphs. The internal publisher validates the materialized graph and checks the retained base reference. Parser settings, answer buttons, and per-outcome prompts remain future work.

After saving a step, reopen it to edit its prompts. Use **Chat wording** to override a supported step's written prompt. For voice, add ordered **Voice segments** with spoken text and a whole-second pause. Arrival segments can listen during a positive pause, and the final custom arrival segment must listen. Keep the placeholders named in the form. Empty fields inherit available shared defaults and otherwise use built-in wording. Clearing a local field restores inheritance. Shared templates can store both channels' fields. This form covers the primary arrival, departure, guests, room, confirmation, delivery, contact-entry, cancellation and handover prompts. Receipt and contact-readback variants and the bilingual welcome need separate treatment.

The structural preview accepts incomplete drafts. The stricter outcome check requires named routes for both delivery methods, the wait and immediate receipt paths, dispatch outcomes, and booking retries and corrections. It checks standalone English and Polish web chat and browser voice. Language switching, legacy drafts and inbound phone are still handled by their existing engines. The publisher protects the saved graph with its database transaction. A future runtime dispatcher must identify outcomes before applying their transitions. Staff can continue changing live wording from the existing prompt editor.

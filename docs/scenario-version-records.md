# Versioned booking scenario records

The reception app stores one scenario per Polish or English chat or voice scope. Each language can also have a shared template. A channel draft records the exact sealed shared version it inherits from in `base_version`. Leaving the field empty makes the draft independent. Shared templates have no parent.

A scenario can retain several versions, each with numbered identity, ordered steps and one destination per event from each source step. The graph belongs to one version. A saved step stays in its original version. Replace a transition to change its endpoints. The future publisher must resolve the shared defaults into a complete graph before sealing a version so changing a shared template never changes an active booking flow. Step configuration currently stores a JSON object. The draft graph validator checks a conservative subset of the existing booking transitions. Structured wording, timing and parser settings still need their own validation before the graph can run.

`published_at` identifies previously sealed versions. The scenario's `published_version` points to the current selection. A future rollback can select a prior sealed version while keeping the retained versions and their graph records available to active conversations. Instance write guards reject attempts to change the selection, seal a version directly or modify a sealed graph. Publication needs a transaction that owns graph mutations, validates ownership and every path, and prevents queryset or concurrent draft writes from changing a sealed graph. These guards do not cover bulk writes or raw SQL. Publish, rollback, audit and conversation pinning remain follow-up work.

The migration only adds empty tables. The existing scenario editor and guest flows continue to use the existing prompts.

## Draft editing and validation

Versioned scenario administration keeps proposed edits separate from live prompt edits. In Django admin, create a **Scenario** for the language and channel, then create a numbered **Scenario version**. Add **Scenario steps** and **Scenario transitions** with the same version. Reopen the version to see **Saved graph validation**. Django applies its usual model permissions to each entry. The validation preview requires permission to inspect both steps and transitions. To replace a transition, delete the draft transition and add its replacement. To remove a draft step, remove its connected transitions first. The version history and a pinned shared base identify exactly which records a draft refers to.

The draft validator checks graph structure and the approval path. It checks that the entry and required booking states exist, that steps are reachable, that events lead to permitted destinations, and that a completed booking can only follow both quote approval and contact approval. It permits explicitly designated same-step retries. This first validator expects a standalone graph with empty per-step configuration. The current validator rejects any shared-base reference. A later validator will need to validate the effective graph while retaining the exact shared version it came from. Prompts, parser settings, and timing need a configuration schema.

Validation is a structural preview of the stored draft. An accepted graph can omit events such as declining a quote, invalid input, or delivery waiting. Publication will need to require applicable outcomes or define safe fallback handling, then repeat the checks inside the database write transaction. The booking engine must identify quote approval, contact approval, and dispatch outcomes before applying their transitions. Staff can continue changing live wording from the existing prompt editor.

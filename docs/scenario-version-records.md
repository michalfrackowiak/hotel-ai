# Versioned booking scenario records

The reception app stores one scenario per Polish or English chat or voice scope. Each language can also have a shared template. A channel draft records the exact sealed shared version it inherits from in `base_version`. Leaving the field empty makes the draft independent. Shared templates have no parent.

A scenario can retain several versions, each with numbered identity, ordered steps and one destination per event from each source step. The graph belongs to one version. A saved step stays in its original version. Replace a transition to change its endpoints. The future publisher must resolve the shared defaults into a complete graph before sealing a version so changing a shared template never changes an active booking flow. Step configuration stores a structured JSON object behind the scenario step form. The draft graph validator checks a conservative subset of the existing booking transitions.

`published_at` identifies previously sealed versions. The scenario's `published_version` points to the current selection. A future rollback can select a prior sealed version while keeping the retained versions and their graph records available to active conversations. Instance write guards reject attempts to change the selection, seal a version directly or modify a sealed graph. Publication needs a transaction that owns graph mutations, validates ownership and every path, and prevents queryset or concurrent draft writes from changing a sealed graph. These guards do not cover bulk writes or raw SQL. Publish, rollback, audit and conversation pinning remain follow-up work.

The migration only adds empty tables. The existing scenario editor and guest flows continue to use the existing prompts.

## Draft editing and validation

Versioned scenario administration keeps proposed edits separate from live prompt edits. In Django admin, create a **Scenario** for the language and channel, then create a numbered **Scenario version**. Add **Scenario steps** and **Scenario transitions** with the same version. Reopen the version to see **Saved graph validation** and **Outcome coverage**. Django applies its usual model permissions to each entry. The validation preview requires permission to inspect both steps and transitions. To replace a transition, delete the draft transition and add its replacement. To remove a draft step, remove its connected transitions first. The version history and a pinned shared base identify exactly which records a draft refers to.

The draft validator checks graph structure and the approval path. It checks that the entry and required booking states exist, that steps are reachable, that events lead to permitted destinations, and that a completed booking can only follow both quote approval and contact approval. It permits explicitly designated same-step retries. Draft steps can use the supported wording and voice segment settings. The current validator expects a standalone graph and rejects any shared-base reference. A later validator will need to validate the effective graph while retaining the exact shared version it came from. Parser settings, answer buttons, and per-outcome prompts remain future work.

After saving a step, reopen it to edit its prompts. Use **Chat wording** to override a supported step's written prompt. For voice, add ordered **Voice segments** with spoken text and a whole-second pause. Arrival segments can listen during a positive pause, and the final custom arrival segment must listen. Keep the placeholders named in the form. Empty fields use the built-in defaults. Shared templates can store both channels' fields. This form covers the primary arrival, departure, guests, room, confirmation, delivery, contact-entry, cancellation and handover prompts. Receipt and contact-readback variants and the bilingual welcome need separate treatment.

The structural preview accepts incomplete drafts. The stricter outcome check requires named routes for both delivery methods, the wait and immediate receipt paths, dispatch outcomes, and booking retries and corrections. It checks standalone English and Polish web chat and browser voice. Language switching, legacy drafts and inbound phone are still handled by their existing engines. A future publisher must protect the graph snapshot with its database transaction, and the booking engine must identify outcomes before applying their transitions. Staff can continue changing live wording from the existing prompt editor.

# Google guest sign-in readiness

Assessment date: 23 November 2026

Public guest sign-in needs a stable HTTPS hostname under a hotel-controlled registrable domain and a hotel-owned Google Cloud project. Production currently serves the reception at `https://92.5.19.10`. A read-only TLS probe confirmed that the existing certificate covers the IP address. Google prohibits public raw IP addresses in web-server OAuth redirect URIs and requires registered authorized domains for production branding and client configuration. The localhost exception is for development. DNS ownership, the final hostname and the production client ID still need confirmation. [Google redirect URI rules](https://developers.google.com/identity/protocols/oauth2/web-server#uri-validation) · [Google authorized domains and branding](https://support.google.com/cloud/answer/15549049?hl=en)

## Integration choice

Use Google Identity Services (GIS) with an explicit Sign in with Google button, the JavaScript popup callback and a same-origin Django POST endpoint. Register the exact HTTPS scheme, host and port of the guest site as an **Authorized JavaScript origin**. The popup sends the ID token to a JS callback and our JS sends it to Django with Django's CSRF header. This flow needs a web client ID and uses neither a redirect registration nor a client secret. Reserve the authorization-code flow for a future feature that needs delegated Google API access. GIS redirect mode is another distinct flow. It POSTs a credential to a registered login URI and uses Google’s documented double-submit cookie check. [GIS setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid) · [GIS integration considerations](https://developers.google.com/identity/gsi/web/guides/integrate)

The project already depends on `google-auth[requests]`. Server code can use `verify_oauth2_token()` with the configured client ID as audience to validate signature, audience, issuer and expiry. Bind a short-lived, single-use nonce to the current browser session and verify it in the returned token. Apply a bounded request size and verification timeout, cache Google signing certificates according to their freshness and exclude credentials from logs and persistence. A Google transport or validation failure should return the guest to the current draft. [Google ID token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token) · [Python verifier](https://googleapis.dev/python/google-auth/latest/reference/google.oauth2.id_token.html) · [GIS nonce field](https://developers.google.com/identity/gsi/web/reference/js-reference#nonce)

Use the validated Google subject (`sub`) as the unique Google identity and enforce uniqueness in the database so concurrent first logins converge on one guest account. Use a guest session with no staff privileges. Avoid automatic account association based on an email claim. Scope any future booking view to explicit, validated ownership and require a separate claim challenge for historical bookings. The existing reception views locate conversations by Django session ID, and deleting that session cascades through the conversation and its staff thread. Use a stable conversation identifier stored server-side in the session, independent of the Django session row, before enabling guest sign-in. Migrate existing conversations and preserve their child records. Carry the identifier through successful session rotation and invalidate access from the old cookie. Clear the association on logout or account switch and define expiry cleanup before removing the cascade. Verify draft, pending booking receipt and active staff handover continuity across chat and voice. [Google subject guidance](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token) · [Django session rotation](https://docs.djangoproject.com/en/5.2/topics/http/sessions/#django.contrib.sessions.backends.base.SessionBase.cycle_key)

## Launch sequence

1. The hotel’s DNS operator confirms an owned hostname, points DNS at the host and verifies control of the registrable domain in Google Search Console when preparing verification. Provision and test TLS and renewal for the hostname. The checked-in [Nginx virtual host](../deploy/nginx/hotel-ai.conf) names the IP, and its [reception snippet](../deploy/nginx/hotel-ai-reception.inc) serves an explicit set of paths. Add the hostname, certificate and only the necessary account, credential POST and policy routes. Set [Django's allowed hosts and trusted proxy scheme](../config/settings.py) for the hostname and verify secure cookies. Keep the IP entry available during transition so existing host-scoped sessions can finish. [Google authorized domains](https://support.google.com/cloud/answer/15549049?hl=en)
2. The hotel’s Google Cloud project owner sets up separate development and production projects and web clients. Use External audience for public guests and prepare the production project for In production. Set the app name, support and developer contacts, the authorized registrable domain and the homepage, privacy policy and terms URLs. The homepage should describe the service and link to the same privacy policy listed in the console. The privacy policy should describe Google identity data use and storage. Complete the console’s brand verification flow for displaying the brand to all users. Identity-only sign-in and basic identity scopes have a Testing exception to the listed-user and seven-day authorization rules. Restrict a pilot at the app if it needs restricted access. [App branding](https://support.google.com/cloud/answer/15549049?hl=en) · [App audience](https://support.google.com/cloud/answer/15549945?hl=en) · [Separate projects and submission](https://support.google.com/cloud/answer/13461325?hl=en)
3. Build and test the identity flow with sign-in disabled by default and a mock verifier, then configure a development client for localhost or a controlled HTTPS staging hostname. Keep login optional and request only basic identity. Leave booking delivery and Calendar permissions out of guest sign-in. The public client ID can be delivered to the browser. Use environment-specific configuration and load the GIS script only for the enabled sign-in UI. Test browser privacy settings and follow Google’s CSP and popup guidance where applicable. [GIS setup and supported headers](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid) · [Google’s minimum-scope guidance](https://support.google.com/cloud/answer/13807380?hl=en)
4. Run a controlled bilingual HTTPS pilot before enabling the production button. Verify new and returning accounts, cancellation and failure without draft loss, invalid and replayed tokens, duplicate first sign-in, logout and expiry, access to admin, and unauthorized booking reads. Validate chat, voice, microphone, speech, health and login on the hostname. Verify that turning off guest sign-in still allows anonymous booking. Test real Google accounts with the development client first, then confirm the production client only on the approved hostname.

The next implementation can start with development fixtures while the hotel confirms DNS and OAuth project ownership. This assessment made no production DNS, certificate, Cloud project or application changes.

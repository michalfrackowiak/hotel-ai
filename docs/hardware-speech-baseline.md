## Recovery and integration status

A read-only SQLite connection backed up the live database into a temporary directory. The copy was reopened, passed `PRAGMA integrity_check`, contained 29 applied migration records, and accepted an isolated table/write/read probe. The temporary copy was deleted. Production data was never printed or changed. This verifies SQLite backup/restore mechanics; full service recovery from an off-host backup remains open.

Environment presence checks returned false for SMTP host/user/password, Twilio account/token/SMS sender and phone reception destination. No rooms have a nonempty Google Calendar link. Hotel owner must provide approved destinations, credentials and controlled recipients; implementation owner then configures and verifies delivery, calendar sync and attended transfer. Do not infer live integration readiness from unit tests.

## Warm synthetic speech results

Raw fictional inputs, transcripts, timings and conditions: [JSON report](speech-baseline-2026-11-15.json). Two repetitions of arrival, duration, guest count, email, phone and silence per language produced 24 completed requests with no transport errors. Speech was generated by Piper and resampled to 16 kHz PCM with linear interpolation before Vosk. The installed deterministic parser checked the intended values; no learned corrections or provider-model fallback were evaluated. Both processes were already warm.

| Metric | English | Polish |
| --- | --- | --- |
| Full WAV response p50 / p95 | 0.283 / 0.753 s | 0.252 / 0.731 s |
| STT response p50 / p95, including silence | 0.607 / 0.958 s | 0.413 / 0.703 s |
| Synthetic generation + resampling + STT p50 / p95 | 0.885 / 1.750 s | 0.655 / 1.477 s |
| TTS real-time factor p50 / p95 | 0.183 / 0.325 | 0.177 / 0.186 |
| STT real-time factor p50 / p95 | 0.421 / 0.680 | 0.293 / 0.393 |
| Semantic success including two silence controls | 10/12 | 9/12 |
| Semantic success excluding silence | 8/10 | 7/10 |

Email failed both repetitions in both languages. Polish arrival `jutro` failed once; durations, guest counts and phone fixtures passed both repeats in each language. Nearest-rank percentiles on these small samples are descriptive only; p95 is effectively the maximum. Pipeline time includes generation of the synthetic guest answer, so it is not the latency of a real booking reply. User-perceived recording, endpointing, browser playback and network latency remain open.

A single Docker stats snapshot during execution saw ASR at 41.8% CPU and 313.8 MiB, Piper at 758.4 MiB and web at 72.91 MiB. This is not a peak measurement. No resource limit was exceeded in the sequential run, but concurrent capacity has not been established.

To reproduce on the private server, copy [benchmark_speech.py](../scripts/benchmark_speech.py) to a temporary path and feed it to the existing web container:

```sh
sudo docker exec -i hotel-ai-web-1 python - --django-semantic \
  --repeats 2 --label deployment-revision < /tmp/benchmark_speech.py > /tmp/baseline.json
```

The script does not create conversations or bookings. It sends fixed fictional phrases directly to the configured private speech services. Run during an idle period because it shares production workers; overlapping guest turns can receive busy responses. For staging/local adapters, use explicit `--piper-url` and `--asr-url` origins. It exits nonzero on transport/format errors, while semantic failures remain visible in the JSON and do not affect the exit code.

## Operating decision and next checks

Retain one inference per speech worker. Keep at least 3 GiB reserved for OS, web/database and margin when admitting replacement models. Treat this as a conservative proposed policy, pending load and peak-memory results. The present two-container bilingual layout avoids duplication. The MacBook's current free memory and disk rule out assuming it can host production replacement models.

Ranked next actions:

1. P0: measure speech semantic errors and false acceptances against real consented staff speech, including noise, dates and contacts. Synthetic speech is only a reproducible smoke baseline.
2. P0: capture peak memory/CPU and web responsiveness under controlled overlapping sessions on a staging deployment; define queue length and user-visible busy behavior.
3. P0: measure cold start and failure recovery on staging, then rehearse full off-host restore without touching live bookings.
4. P1: confirm separate PC/macOS hardware, Docker resources and sustained thermal behavior before enabling a remote worker host.
5. P1: configure and verify delivery/calendar/phone integrations with hotel-approved credentials.

The roadmap's two-second speech-start and three-second STT targets are provisional. Buffered WAV completion time is not browser time-to-first-audio. No multi-session capacity claim is made by the sequential baseline.

## Inventory reproduction

On the server, run `uname -m`, `lscpu`, `free -m`, `df -h /`, `sudo docker version`, and `sudo docker stats --no-stream`. Use Docker inspect's image, memory, NanoCPUs and StartedAt fields; do not export container environment values. On Windows, use `Get-CimInstance` for `Win32_Processor`, `Win32_ComputerSystem` and `Win32_OperatingSystem`, `Get-PSDrive C`, and Docker info's architecture, NCPU, MemTotal and ServerVersion fields.
